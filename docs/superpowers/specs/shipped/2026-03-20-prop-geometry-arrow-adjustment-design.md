# Prop Geometry Arrow Adjustment Tier

**Date:** 2026-03-20
**Status:** Design
**Problem:** Arrow positions overlap prop bodies for non-staff props (triads, fans, buugeng, etc.) because the existing adjustment pipeline has no letter-free, prop-aware tier.

---

## Problem Statement

The arrow positioning pipeline has four tiers:

1. **Default** (JSON) — keyed by motionType + positionType + layer + turns. No prop awareness.
2. **Special** (JSON) — keyed by letter + oriKey + turnsTuple + arrowKey. No prop awareness.
3. **Global** (Firestore) — keyed by letter + oriKey + turnsTuple + arrowKey + propType. Prop-aware but letter-specific.
4. **Manual** (WASD) — per-beat pixel offsets. Not reusable.

When triads (or other wide/tall props) sit at beta with radial orientations (in/out), the prop geometry extends into the arrow's default position. The arrow visually overlaps the prop body. This happens regardless of letter — it's a property of the prop's physical shape combined with the orientation.

Today, the only fix is either:
- Set a Global adjustment for every individual letter (hundreds of entries)
- Use WASD per-beat (not reusable at all)

Neither scales. The system needs a tier that says: "For triads at beta with orientation X, always nudge the arrow by this much" — independent of letter.

---

## Design

### New Tier: Prop Geometry Adjustments

A Firestore-backed lookup tier that sits between Default and Special in the cascade. It captures adjustments that apply to **all letters** sharing the same prop-type + orientation + position geometry.

**Cascade (highest priority first):**

```
Priority 5 (highest): Manual adjustments (WASD, per-beat additive)
Priority 4: Global adjustments (Firestore, letter+prop specific)
Priority 3: Special placement (JSON, letter-specific)
Priority 2: ★ Prop Geometry adjustment (Firestore, letter-free, prop-aware) ← NEW
Priority 1 (lowest): Default placement (JSON, motion-type based)
```

**Lookup order:** The pipeline checks from highest to lowest priority. Special placement (with global override) is checked first. If nothing matches, prop geometry is checked. If that also misses, the default placement is used. Manual WASD is additive on top of everything.

**Why `endOri`/`otherEndOri` instead of `oriKey`:** The existing `oriKey` (e.g., `from_layer1`) is generated by `SpecialPlacementOriKeyGenerator` and groups orientation combos coarsely — `in|out`, `out|out`, and `in|in` are all `from_layer1` (both radial). But for prop geometry, these are visually distinct scenarios. A triad ending "out" extends differently than one ending "in." Raw orientations give the granularity this tier needs.

**PropType granularity:** Uses exact `PropType` enum values (lowercase). `bigtriad` and `triad` have different physical geometries and may need different adjustments. No family-level normalization.

**Caching strategy:** Same load-all-on-init + real-time-subscription pattern as `GlobalArrowAdjustmentRepository`. With expected entry counts of 10-30 per prop family, the full cache is trivially small.

### Key Structure

**Firestore collection:** `prop_geometry_adjustments`

**Document key format:**
```
{gridMode}|{propType}|{otherPropType}|{positionType}|{endOri}|{otherEndOri}|{motionType}|{turns}|{arrowColor}
```

**Example keys:**
```
diamond|triad|triad|beta|out|in|pro|1|blue      → { adjustmentX: 20, adjustmentY: -50 }
diamond|triad|triad|beta|out|out|pro|1|blue      → { adjustmentX: 30, adjustmentY: -40 }
diamond|triad|triad|beta|in|in|pro|1|blue        → { adjustmentX: 0, adjustmentY: 0 }
diamond|fan|fan|beta|out|in|anti|0.5|red          → { adjustmentX: -15, adjustmentY: 25 }
```

### Key Dimensions

| Dimension | Source | Values |
|-----------|--------|--------|
| `gridMode` | Derived from motion locations | `diamond`, `box` |
| `propType` | `motionData.propType` of the arrow's hand | Any `PropType` enum value |
| `otherPropType` | `otherMotion.propType` | Any `PropType` enum value |
| `positionType` | Derived from `endPosition` | `alpha`, `beta`, `gamma` |
| `endOri` | `motionData.endOrientation` of arrow's hand | `in`, `out`, `clock`, `counter` |
| `otherEndOri` | Other hand's `endOrientation` | `in`, `out`, `clock`, `counter` |
| `motionType` | `motionData.motionType` | `pro`, `anti`, `float`, `dash`, `static` |
| `turns` | `motionData.turns` | `0`, `0.5`, `1`, `1.5`, `2`, `2.5`, `3`, `fl` |
| `arrowColor` | Which arrow is being adjusted | `blue`, `red` |

### Why Each Dimension Matters

- **propType + otherPropType**: A triad next to a triad overlaps differently than a triad next to a staff. The prop combo determines the geometry.
- **positionType**: Beta (same endpoint) has both props stacked, so overlap is worst. Alpha/gamma have props at different locations — may not need adjustment at all.
- **endOri + otherEndOri**: `out|in` vs `out|out` vs `in|in` create different visual profiles. When one triad points "out," its arms extend toward where the arrow sits. When both point "out," beta offset pushes them apart, changing the geometry entirely.
- **motionType + turns**: A pro-1 arrow sits in a different default position than an anti-0.5 arrow. The overlap depends on where the arrow lands.
- **arrowColor**: Blue and red arrows at the same location get different positions (one inner, one outer in collision scenarios).

### Cascading Within the Tier

The prop geometry tier has its own internal fallback chain using `"*"` as a wildcard value. All keys remain 9 parts — wildcards replace specific values:

```
1. Full key:                gridMode|propType|otherPropType|positionType|endOri|otherEndOri|motionType|turns|arrowColor
2. Wildcard arrowColor:     gridMode|propType|otherPropType|positionType|endOri|otherEndOri|motionType|turns|*
3. Wildcard otherPropType:  gridMode|propType|*|positionType|endOri|otherEndOri|motionType|turns|arrowColor
4. Wildcard both:           gridMode|propType|*|positionType|endOri|otherEndOri|motionType|turns|*
5. No match → fall through to Default tier
```

This means you can set an adjustment for "all triads at beta with out orientation, pro 1 turn" (using `*` for otherPropType and arrowColor) without specifying the other prop type or color. But if triads-next-to-fans need something different from triads-next-to-triads, the more specific entry wins.

**Interaction with ArrowCollisionResolver:** The collision resolver is a separate system used only for hand-path cards in `DeckFamilySection`. It does not run in the main pictograph rendering pipeline where prop geometry adjustments are applied. They do not interact.

### Domain Model

```typescript
interface PropGeometryAdjustment {
  readonly gridMode: string;
  readonly propType: string;
  readonly otherPropType: string;
  readonly positionType: string;       // "alpha" | "beta" | "gamma"
  readonly endOrientation: string;     // "in" | "out" | "clock" | "counter"
  readonly otherEndOrientation: string;
  readonly motionType: string;
  readonly turns: string;              // "0" | "0.5" | "1" | ... | "fl"
  readonly arrowColor: string;         // "blue" | "red"
  readonly adjustmentX: number;
  readonly adjustmentY: number;
  readonly updatedAt: Timestamp;
  readonly updatedBy: string;
}
```

### Integration Point

In `ArrowAdjustmentCalculator.calculateAdjustmentResult()`, between the base adjustment lookup and the directional tuple transformation:

```
Current flow:
  1. getBaseAdjustment() → special (with global override) → default
  2. processDirectionalTuples(baseAdjustment, ...)
  3. Return final point

New flow:
  1. getBaseAdjustment() → special (with global override) → prop geometry → default
  2. processDirectionalTuples(baseAdjustment, ...)
  3. Return final point
```

The prop geometry lookup happens inside `getBaseAdjustment()`. If a special placement or global adjustment exists for the specific letter, those take priority (they're checked first). If neither exists, the prop geometry tier is checked before falling back to the generic default.

**Critical detail:** The adjustment value stored in the prop geometry tier is a **base adjustment** — the same format as special placement values. It gets run through `processDirectionalTuples()` for quadrant rotation, so one entry covers all four quadrants (N/E/S/W or NE/SE/SW/NW).

### Position Type Derivation

Position type comes from the pictograph's `endPosition` field, which classifies the relationship between both hands' end locations:

| End Position | Meaning |
|-------------|---------|
| `alpha` | Hands at opposite grid points |
| `beta` | Hands at same grid point |
| `gamma` | Hands at adjacent grid points (right angle) |

### Authoring Workflow

1. User sees a pictograph with arrow-prop overlap, brings it to Claude with data dump
2. Claude and user identify the scenario dimensions from the pictograph data
3. Claude writes the adjustment to Firestore via a seed script or direct write
4. User verifies on the live app
5. If other pictographs are affected, review and adjust

The WASD workflow is completely untouched. It continues to work for per-beat manual fixes. The prop geometry tier provides better defaults so WASD is needed less often.

### Seed Script

A Node.js script (`scripts/seed-prop-geometry-adjustments.ts`) for batch-writing adjustments:

```typescript
// Usage: npx tsx scripts/seed-prop-geometry-adjustments.ts
// Reads from a JSON file of adjustments and writes them to Firestore
```

This is how Claude populates adjustments after discussing scenarios with the user.

### Finite Scenario Space

For any given prop type pair (e.g., triad + triad):
- 3 position types (alpha, beta, gamma)
- 4 end orientations × 4 other end orientations = 16 combos (but symmetric, so ~10 unique)
- 5 motion types
- 7 turn values
- 2 colors

**Theoretical max:** ~2,100 entries per prop pair. In practice, most don't cause visual overlap. The user will encounter and fix maybe 10-30 per prop family over time, building up the adjustment set organically.

### What This Does NOT Change

- Default placement JSON files — untouched
- Special placement JSON files — untouched
- Global adjustment Firestore collection — untouched
- WASD keyboard adjuster — untouched
- ArrowCollisionResolver — untouched (separate concern for hand-path cards)
- Beta offset calculation — untouched (the prop geometry tier accounts for beta offset's effects by having separate entries for different orientation combos)

## Testing Strategy

Unit tests for:
- Key generation and parsing (round-trip)
- Internal cascading lookup (full key → drop arrowColor → drop otherPropType → null)
- Integration with `ArrowAdjustmentCalculator` — verify prop geometry tier is checked between special and default
- Verify higher tiers (special, global) still override prop geometry

No visual tests — the user is the visual verification authority.
